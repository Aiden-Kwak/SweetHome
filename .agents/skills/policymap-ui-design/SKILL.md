# PolicyMap UI 설계

## 목적

PolicyMap 화면은 가격 예측값을 보여주는 대시보드가 아니라, 정책입안자가 적용 범위, 보완 대상과 시행 순서를 비교하는 사전 영향평가 도구여야 한다. 개인 사용자는 같은 결과에서 자신의 대출 가능액과 선택 가능한 지역의 변화를 확인한다.

## 작업 전에 읽을 문서

1. `GEMINI.md`의 제품 불변 규칙을 읽는다.
2. `docs/PRODUCT_SPEC.md`에서 사용자, 핵심 경험, 주요 화면과 신뢰도 규칙을 확인한다.
3. 발표 흐름을 바꾸면 `docs/FINAL_DEMO.md`를 읽는다.
4. API 계약이나 상태값을 바꾸면 `docs/DATA_MODEL.md`와 `docs/ARCHITECTURE.md`를 읽는다.
5. 실제 화면을 설계하거나 검토할 때는 [UI 방법론](references/methodology.md)을 전체 읽는다.

## 핵심 판단 순서

1. 이 화면에서 사용자가 내릴 하나의 판단을 먼저 적는다.
2. 정책의 기존 상태와 변경 상태를 비교한다.
3. 지역별 결과와 가구 유형별 반응이 같은 `scenario_id`를 사용하는지 확인한다.
4. 결과 숫자보다 원인 경로와 근거 범위를 먼저 설명한다.
5. 정책 완전성, 데이터 상태, 모델 상태와 한계를 주요 결과 근처에 놓는다.
6. 키보드, 초점, 명도 대비와 색상 이외의 구분 수단을 검증한다.

## 반드시 지킬 규칙

- 합성 데이터, 검증되지 않은 계수와 예시 결과를 실제 전망처럼 표시하지 않는다.
- 단일 예측값보다 범위, 시간 축과 적용 조건을 함께 표시한다.
- 정책 원문, 시행일, 적용 지역, 대상, 예외와 검증 상태로 돌아갈 수 있게 한다.
- JEV 가구 유형을 감정적인 챗봇 페르소나로 표현하지 않는다. 구매 가능액, 선택 지역, 행동 확률과 제약 조건을 비교한다.
- 지도와 가구 패널을 별도의 결과 화면으로 분리하지 않는다. 선택과 강조 상태를 양방향으로 연결한다.
- React 컴포넌트에 정책 판정, 데이터 접근이나 시뮬레이션 로직을 넣지 않는다.
- 장식용 이모지, 불필요한 카드 반복, 의미 없는 그라데이션과 지나친 애니메이션을 사용하지 않는다.

## 구현과 검증

1. 기존 `apps/web/src/App.tsx`와 `styles.css`를 먼저 읽고 재사용할 패턴을 확인한다.
2. 가장 작은 완결된 사용자 흐름을 구현한다.
3. 로딩, 빈 결과, 오류, 데이터 불완전과 모델 사용 불가 상태를 별도로 확인한다.
4. 정량 결과 근처에 `data_status`, `model_status`, 기준 시점, 단위와 한계가 보이는지 확인한다.
5. UI가 바뀐 경우 브라우저에서 주요 흐름을 직접 검증한다.
6. `make check`를 실행한 뒤 변경한 행동, 검증 결과와 남은 제약을 보고한다.
