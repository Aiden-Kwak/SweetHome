# PolicyMap UI 방법론

## 1. 의사결정 중심의 정보 구조

화면을 정책 문서, 지도, 그래프처럼 자료 형식으로 나누지 말고 사용자의 판단 순서로 구성한다.

```mermaid
flowchart LR
    A[정책 원문] --> B[기존 정책과의 차이]
    B --> C[적용 지역과 가구]
    C --> D[시간별 결과 범위]
    D --> E[원인 경로]
    E --> F[근거와 한계]
    F --> G[범위, 보완, 시행 순서 결정]
```

각 화면은 다음 질문 중 하나를 가장 먼저 답해야 한다.

- 무엇이 바뀌었는가?
- 어디에 적용되는가?
- 누가 더 크게 영향을 받는가?
- 어떤 경로로 결과가 나타나는가?
- 이 결과를 어디까지 믿을 수 있는가?
- 적용 범위, 보완 대상과 시행 순서를 어떻게 바꾸어야 하는가?

## 2. 화면 체계

### 정책 입력

- 문서 드롭 영역과 본문 붙여넣기를 하나의 주요 행동으로 보여준다.
- 파일명, 공식 출처, 발표일, 해시, 추출 상태를 보이게 한다.
- 문서 추출을 실제로 완료한 후에만 완료 상태를 표시한다.
- 발표용 검증 스냅샷을 사용하면 캐시 사용 상태를 숨기지 않는다.

### 정책 차이

- 신규, 강화, 완화, 연장, 종료, 대체와 정정을 원자 규칙 단위로 표시한다.
- 반드시 변경 전과 후의 값, 적용 지역, 대상, 시행일, 예외, 원문 위치와 검증 상태를 포함한다.
- 발표에서는 영향이 큰 변경 최대 3개만 펼쳐 보여주고, 나머지는 추가 변경점으로 접는다.
- 추출된 후보와 사람이 확정한 규칙을 색상, 레이블과 문구로 구분한다.

### 통합 시뮬레이션

- 데스크톱 발표 기준으로 지도가 약 60%, 가구 패널이 약 28%를 차지하도록 한다.
- 상단에 정책 변경 요약과 3개월, 6개월, 12개월 선택을 놓는다.
- 하단에 선택한 지역의 원인 경로를 수평으로 연결한다.
- 지도, 가구 유형과 원인 경로는 같은 `scenario_id`, 기준 시점, 데이터 버전과 모델 버전을 사용한다.

### 근거 패널

- 선택한 결과에 기여한 정책 규칙, 연구 `Claim`, 데이터 필드와 모형 버전을 같은 경로에서 보여준다.
- 연구의 지역, 기간, 방법, 정책 유형과 시차가 현재 시나리오와 맞는지 표시한다.
- 상반된 근거를 평균으로 지우지 말고 각각의 조건부 결과로 보여준다.

## 3. 시각 계층과 조작 원칙

사용자가 화면을 다시 읽지 않고도 핵심을 알 수 있게 한다. 일반적인 모바일 금융 서비스의 명확한 계층 패턴을 참고하되, 표면적인 모양을 복제하지 않는다.

- 한 화면에는 하나의 주요 질문과 하나의 주요 행동만 강조한다.
- 핵심 결과, 초점이 돼야 할 제어, 보조 설명, 메타데이터 순으로 명도 대비를 낮춘다.
- 카드는 다른 정보 단위를 구분할 때만 사용한다. 단순한 여백이나 선으로 충분한 내용을 카드에 넣지 않는다.
- 사용자가 먼저 알아야 할 내용을 펼쳐 보여주고, 상세 근거와 메타데이터는 선택 후 공개한다.
- 변화를 설명하는 애니메이션은 160ms에서 240ms 정도로 짧게 사용한다. `prefers-reduced-motion`에서는 축소하거나 제거한다.
- 색상은 상승과 하락, 직접효과와 전이효과, 검증과 경고 중 하나의 의미만 담는다.

### 기본 시각 토큰

| 용도 | 값 | 사용 원칙 |
| --- | --- | --- |
| 본문 | `#191F28` | 제목과 핵심 수치에 사용한다. |
| 보조 문자 | `#6B7684` | 설명과 메타데이터에 사용한다. |
| 주요 동작 | `#3182F6` | 선택, 초점과 주요 행동에 사용한다. |
| 주요 동작 배경 | `#E8F3FF` | 선택된 규칙과 보조 영역에 사용한다. |
| 경고 | `#F04452` | 불완전, 한계와 사용 불가 상태에만 사용한다. |
| 경계선 | `#E5E8EB` | 카드보다 정보 단위를 약하게 나눈다. |
| 화면 배경 | `#F7F8FA` | 내용을 반복하지 않고 층위만 구분한다. |

- 기본 여백 단위는 8px이며 8, 16, 24, 32, 48, 64px 단계를 우선한다.
- 본문은 최소 16px, 보조 라벨은 최소 12px을 유지한다.
- 한국어 제목과 본문은 `word-break: keep-all`과 충분한 행간을 사용한다.
- 반지름은 컴포넌트 크기에 따라 10px에서 26px 범위를 사용하되, 서로 다른 수치를 남용하지 않는다.

## 4. 지도 설계

- 한 번에 가격, 거래량, 대출가능액 중 하나의 주요 지표만 색상으로 표현한다.
- 범례에는 단위, 기준 시점, 경과 기간, 중앙값인지 범위인지, `data_status`와 `model_status`를 표시한다.
- 직접 적용 지역과 인접 전이 지역은 색상 외에 선, 패턴, 라벨 중 하나로도 구분한다.
- 상승과 하락을 양방향으로 보여줄 때는 0을 중심으로 하는 발산형 색상을 사용한다.
- 지역을 선택하면 가구 카드와 원인 경로가 같이 갱신되어야 한다.
- 지도 타일이 끊겨도 시연할 수 있도록 수도권 경계와 최소 라벨을 로컬 자원으로 보유한다.

## 5. 가구 유형 패널

기본 비교 집단은 무주택 신혼부부, 고DSR 실수요자, 1주택 갈아타기 가구와 현금 비중이 높은 다주택자이다. 정책 특성에 맞지 않으면 집단을 조정하되, 화면에 노출하는 집단은 최대 4개를 우선한다.

각 카드에는 다음 정보를 우선한다.

1. 정책 전과 후의 구매 가능액
2. 선택 가능한 지역의 변화
3. 매수, 매도, 임대, 증여와 관망 중 행동 확률의 변화
4. 지배적인 제약 조건
5. 결과의 전제, 기준 시점과 모델 상태

자유로운 대화문, 감정 표현, 사람의 얼굴 이미지보다 상태 비교와 제약 조건을 우선한다.

## 6. 원인 경로

원인 경로는 결과를 합리화하는 자연어 설명이 아니라, 추적 가능한 상태 연결이어야 한다.

```mermaid
flowchart LR
    R[정책 규칙] --> M[대출 가능액과 세후수익률]
    M --> B[가구 행동]
    B --> S[수요 이동과 거래량]
    S --> O[지역별 결과 범위]
```

- 각 노드는 정책 규칙, 계산 및 모형, 행동 상태와 지역 결과 중 하나에 대응해야 한다.
- 노드를 선택하면 원문 위치, 입력 필드, 계산 방식 및 연구 `Claim`을 열 수 있게 한다.
- 방향이 불확실하거나 근거가 없는 연결은 확정적인 화살표로 표현하지 않는다.

## 7. 신뢰와 상태 표시

다음 상태를 하나의 종합 점수로 합치지 않는다.

- 정책 완전성
- 데이터 완전성
- 근거 적합성
- 모델 재현성

상태는 다음 위치에 놓는다.

- 전체 데모 상태는 고정 배너에 놓는다.
- 정량 결과의 `data_status`와 `model_status`는 결과 제목 또는 범례 옆에 놓는다.
- 특정 규칙의 검증 상태는 정책 차이 카드에 놓는다.
- 연구의 한계와 외적 타당성은 근거 패널에 놓는다.

## 8. 반응형과 접근성

- 태블릿에서는 지도 아래에 가구 패널을 놓고, 선택한 가구의 영향 지역을 지도에 유지한다.
- 모바일에서는 복잡한 지도 편집보다 주요 지역 요약과 가구별 비교를 먼저 보여준다.
- 키보드만으로 탭, 지역, 가구 카드와 근거 패널을 선택할 수 있어야 한다.
- 모든 상호작용에 보이는 초점 표시를 제공한다.
- 색상으로 정보를 구분하면 문구, 아이콘, 패턴 또는 선 중 하나를 추가한다.
- 지도의 지역별 결과는 표 또는 목록으로도 접근할 수 있게 한다.
- 로딩, 오류, 빈 결과와 사용 불가 상태에 `aria-live` 또는 적절한 라이브 영역을 사용한다.

## 9. 문구 작성

- 기능 이름보다 사용자가 답하려는 질문을 제목으로 쓴다.
- 단정적인 `예측`과 `결과`보다 `시나리오`, `범위`, `가능성`과 `근거`를 사용한다.
- 상승과 하락 표시에는 기준 시나리오, 기간과 단위를 함께 적는다.
- 상태 코드만 보여주지 말고 사용자가 다음에 할 일을 완전한 한국어 문장으로 설명한다.
- 사용자 화면에서 `페르소나 에이전트`보다 `가구 유형`과 `예상 반응`을 우선한다.

## 10. 피해야 할 패턴

- 예측 숫자만 크게 보여주고 조건과 한계를 숨기는 화면
- 정책 원문과 연결되지 않은 요약 문구
- 지도의 모든 지표를 동시에 색상으로 표시하는 것
- 상승과 하락, 신뢰와 위험을 색상으로만 구분하는 것
- 지도와 가구 패널이 서로 다른 시나리오나 기준 시점을 사용하는 것
- 가구 유형을 대화형 캐릭터로 꾸며 비교 가능한 상태를 숨기는 것
- 빈 카드, 유사한 배지, 태그와 그래프를 반복해 중요도를 흔드는 것
- 데모 결과임을 알리는 문구를 주석이나 맨 아래에만 놓는 것
- 클라이언트에 정책 판정과 시뮬레이션 로직을 넣는 것

## 11. 완료 점검

- [ ] 주요 사용자와 이 화면의 판단이 한 문장으로 설명된다.
- [ ] 정책 변경 전과 후의 값과 시행 조건을 확인할 수 있다.
- [ ] 지도, 가구 유형과 원인 경로가 같은 시나리오를 사용한다.
- [ ] 범례에 단위, 기준 시점, 경과 기간과 모델 상태가 있다.
- [ ] 실제 결과와 합성, 캐시 또는 예시 결과가 명확히 구분된다.
- [ ] 결과에서 정책 원문, 연구 `Claim`, 데이터와 모형 버전으로 돌아갈 수 있다.
- [ ] 색상 없이도 핵심 상태를 구분할 수 있다.
- [ ] 키보드 초점과 읽히는 한국어 문구를 검증했다.
- [ ] 오류, 빈 결과, 로딩과 불완전 상태를 검증했다.
- [ ] 브라우저에서 주요 흐름을 직접 확인했다.
- [ ] `make check`가 통과했다.
